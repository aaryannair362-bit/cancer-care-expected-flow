## C.15.0 — Radiotherapy module design principles `[PRODUCT]`

**RT-001** — The **RT Prescription** is the authorising clinical object for the delivery of ionising radiation. It is versioned, signed by the Radiation Oncologist, and is the single source against which every plan, every QA check and every fraction is validated. No plan, no QA record and no delivered fraction may exist without an explicit reference to a specific prescription **version**.

**RT-002** — **Prescription, Plan and Delivery are three separate versioned objects** with a strict dependency chain: Prescription vn → Plan vm (built against vn) → QA (performed against Plan vm and Prescription vn) → Released plan → Fractions delivered (each recording the plan version used). Changing an upstream object invalidates downstream approvals rather than silently propagating (`PHY-011`).

**RT-003** — **Prescribed dose and delivered dose are never the same field** (`GEN-CMP-001`). Cumulative delivered dose is computed from actual delivery records, never from fraction count × prescribed dose per fraction, because partial and aborted fractions exist.

**RT-004** — Where the product integrates with an external Treatment Planning System and Record-and-Verify system `[INTEGRATION]`, the HIS/EMR remains the authoritative source for the **prescription, the clinical decisions, the OTV record and the completion summary**; the TPS/R&V remains authoritative for geometric plan data and machine delivery records. The interface contract must specify which system owns each field, and the HIS must display the provenance of imported values.

**RT-005** — Multi-phase and multi-site courses are first-class. A course may contain several phases (e.g. an initial volume followed by a boost) and several anatomical sites treated concurrently or sequentially. Every dose, constraint and cumulative calculation must be attributable to a specific phase and site, and the course-level totals must be derivable.

## C.16.2 · `SCR-PHY-002` — Prescription–Plan Concordance Check

**Purpose:** Verify, field by field, that the plan implements the prescription.
**Table — exact columns:** Parameter · **Prescription value** (read-only, version-stamped) · **Plan value** (imported, `[INTEGRATION]`) · Match `[DERIVED]` (Y/N) · Tolerance where numeric · Deviation · Comment · Checked by · Checked at.
**Rows (minimum):** treatment site; laterality; phase; modality; technique; energy; total dose; number of fractions; dose per fraction; prescription point/normalisation; target volume names and their prescribed doses; fractions per day; patient position; immobilisation; bolus; motion management; image guidance modality and frequency; treatment unit.
**PHY-020 [PRODUCT]** — laterality and site mismatch must be a hard stop, not a warning. These are the errors that produce wrong-site treatment.
**Actions:** Import plan values · Recheck · Record mismatch · Raise discrepancy · Pass concordance.
**Alerts:** Any mismatch on a safety-critical row (site, laterality, dose, fractions, dose/fraction, technique) → hard stop and mandatory discrepancy record.

## C.16.8 · `SCR-PHY-008` — QA Sign-off & Plan Release

**Purpose:** The single gate that permits a plan to be delivered.
**Prerequisite panel (each** **`[DERIVED]`****, with link and outcome):** Prescription signed and current version; RO plan approval against that version; concordance check passed; independent dose verification passed; constraint verification passed; deliverability check passed; patient-specific QA passed (or waived with recorded authority and reason `[CCA CONFIG]`); R&V transfer verified; no open discrepancies above threshold.
**Fields:** Overall outcome; waivers applied (item, authority, reason); physicist signature (re-authenticated); release date/time; released to unit(s); release reference; notes to RTT.

**Downstream:** State → `QA PASSED / RELEASED`; enables `SCR-RO-008` authorisation; appears on RTT unit schedule.

## C.17.1 · `SCR-RTT-001` — Treatment Unit Schedule

## C.17.2 · `SCR-RTT-002` — Pre-Treatment Verification

**Purpose:** The daily gate before any beam is delivered.
**Fields:** **Identity verification** (photograph displayed; minimum two identifiers, method recorded, per `MAR-007` pattern); **Site and laterality confirmation** (explicit affirmative action, displayed in large type, R — `RTT-101`); Fraction number confirmation `[DERIVED]` with mismatch hard stop (**RTT-020 [PRODUCT]**: the system computes the expected fraction number from the delivery history; an RTT-entered fraction number that disagrees halts the workflow); Prescription version current (auto-check); Plan version released (auto-check); Authorisation to treat present (auto-check); Daily preparation confirmed (bladder/bowel/fasting as applicable); Pregnancy re-check where applicable and per configured frequency `[CCA CONFIG]`; Patient condition/concerns reported today (free text + escalate action); RO instructions outstanding (displayed, acknowledged); Devices present (mask/vac-bag/etc. retrieved and IDs matched).
**Alerts:** Hard stop on any auto-check failure; hard stop on identity or fraction mismatch; warning on patient-reported new symptoms (prompts toxicity note and RO escalation).
